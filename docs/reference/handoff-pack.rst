The hand-off pack
===================

Every build writes a ``handoff`` folder next to the ``.pbip`` file. It holds
what a data engineer needs to build the model for real, generated from the
same spec as the model itself. For the hospital example:

::

    out/Hospital/
        Hospital.pbip
        Hospital.SemanticModel/
        Hospital.Report/
        handoff/
            SPEC.md
            manifest.json

``Hospital.Report`` is a report with one empty page and no visuals;
:doc:`cli` lists every file in the build.

Both hand-off files are deterministic: tables, relationships and measures
are sorted and nothing carries a timestamp, so rebuilding an unchanged
spec leaves them byte-identical and a change shows up as a clean diff.
Pass ``--no-handoff`` to ``pbip-forge build`` (or ``handoff=False`` to
``build_pbip``) to skip them.

The build command
------------------

``pbip-forge build`` takes the spec first and the output folder second.
From the root of the tool's repository:

::

    pbip-forge build scripts/build_hospital.py out/Hospital --check --profile handoff
    Built PBIP: out/Hospital/Hospital.pbip

``--check`` judges the spec before anything is written, and a spec with a
P0 or P1 violation writes nothing at all. ``--profile`` chooses the
strictness the check runs under: ``mockup`` by default, ``handoff`` for a
model you are about to hand over. :doc:`../how-to/build-a-model-from-a-spec`
goes from a spec you write to the hand-off, step by step.

SPEC.md
---------

The human-readable spec. The skills show it to you instead of drawing a
diagram by hand, so the diagram always matches the model. It starts with
the line ``Generated by pbip-model-forge 1.2.1 from the model's spec
dict. Regenerate it rather than editing it by hand.`` and contains:

- A Mermaid ``erDiagram`` of every table and relationship. Solid lines are
  active relationships, dotted lines inactive ones; key columns are marked
  ``PK`` and foreign keys ``FK``.
- A table list with each table's role (fact, dimension, calendar or
  measures) and description.
- A data dictionary per table: every column with its type, key, visibility,
  format and description, and the calendar's date range.
- The relationships, with active and filter-direction flags.
- The measures, with their display folder, format, description and DAX.

The top of the hospital example's diagram:

::

    erDiagram
        __Calendar ||--o{ Encounters : "admission_date"
        Departments ||--o{ Encounters : "department_id"
        Diagnoses ||--o{ Encounters : "diagnosis_id"
        __Calendar ||..o{ Encounters : "discharge_date"
        Patients ||--o{ Encounters : "patient_id"
        Physicians ||--o{ Encounters : "physician_id"
        InsuranceCompanies ||--o{ Patients : "insurance_company_id"

GitHub draws the Mermaid block as a diagram when it shows ``SPEC.md``.

manifest.json
---------------

The same model, machine-readable, for a data-engineering tool or a Claude
Code skill to build from. Top-level keys:

.. list-table::
   :widths: 20 80
   :header-rows: 1

   * - Key
     - Contents
   * - ``model``
     - The model name.
   * - ``generator``
     - The tool and version that wrote the file, for example
       ``pbip-model-forge 1.2.1``.
   * - ``tables``
     - One entry per table: ``name``, ``role``, ``description``,
       ``hidden`` and ``columns`` (each with ``name``, ``dataType``,
       ``key``, ``hidden``, ``format``, ``description``). Data tables also
       carry ``sample_rows``, the number of sample rows; the calendar
       carries its ``range`` (``start`` and ``end``).
   * - ``relationships``
     - ``from`` (many side), ``to`` (one side), ``active``, and
       ``crossFilter`` (``single`` or ``both``).
   * - ``measures``
     - ``name``, ``table``, ``expression``, ``format``, ``displayFolder``,
       ``hidden``, ``description``, and ``dependsOn``: the ``measures``,
       ``columns`` and ``tables`` the DAX refers to.

A measure entry from the hospital example:

::

    {
      "dependsOn": {
        "columns": [],
        "measures": [
          "Patients #",
          "Total Billed Revenue"
        ],
        "tables": []
      },
      "description": "Average billed amount per distinct patient seen.",
      "displayFolder": "Ratios",
      "expression": "DIVIDE([Total Billed Revenue], [Patients #])",
      "format": "$ #,0.00",
      "hidden": false,
      "name": "Avg Billed per Patient",
      "table": "Clinic Measures"
    }

The manifest records how many sample rows each table has, not the rows
themselves; the rows are inside the model's table files.

Table roles
-------------

The role comes from the spec. A table on the "one" side of any relationship
is a dimension; a table only on the "many" side is a fact; a table in no
relationship is a dimension; the calendar and the measures table have
their own roles. A spec can set ``"role"`` on a table to override the
inference (:doc:`spec-format`).
